# Governed Semantic Analytics Copilot (V1)

An open-core prototype of a **governed semantic analytics agent**.

Users ask natural-language questions like:

> "Show spend vs the rest of the company by month"
>
> "Show top 10 vendors by spend"

...and get answers backed by:
- **dbt semantic models & metrics** (as the source of truth)
- **Deterministic SQL generation** (no free-form querying)
- **LLM routing** (Ollama-compatible) constrained to governed metrics
- **Insight Packs**: reusable, contract-driven analytics cards (comparison, top-N)

This is a semantic, contract-driven analytics system: the LLM can only select from what you define in dbt.

---

## What's in V1

### Supported (V1)
- **Ask -> governed metric chart** (single metric)
- **Ask -> governed comparison** (spend vs spend)
- **Ask -> ratio metric** (share as %)
- **Packs**: comparison pack (2 metrics + KPIs + narrative); top-N ranking pack (metric + dimension + N)
- **Metrics discovery** (`/metrics`, `/semantic-models`)
- **Deterministic SQL execution** (Databricks SQL Warehouse)
- **LLM eval harness** (routing regression tests)
- **Logging + basic caching**

### Not supported (V1)
- Forecasting / prediction
- Root-cause analysis ("why")
- Arbitrary SQL, table browsing, raw data dumps
- Unit-mixed comparisons (e.g. % vs GBP) - returns `unknown` by design
- Enterprise features (RBAC, audit trails, approval workflows)

---

## Architecture (V1)

**Natural language -> Router (Ollama) -> governed metric(s) -> SQL -> Databricks -> chart + KPIs**

- **dbt** defines the contract (semantic model + metrics)
- The backend reads `dbt/target/manifest.json`
- The LLM is constrained to metric names from that manifest
- SQL is generated deterministically and executed on the warehouse
- UI renders line or bar charts depending on response contract

## Quickstart (Demo dataset)

## Prerequisites
- Docker + Docker Compose
- A Databricks SQL Warehouse (or replace with your adapter later)
- Ollama (runs in Docker in this repo)

## 1) Clone

```bash
git clone https://github.com/demecode/llm_semantic_layer.git
cd llm_semantic_layer
```

## 2) Configure environment variables

```bash
cp .env.example .env
```

Edit `.env`:

```dotenv
DATABRICKS_SERVER_HOSTNAME=dbc-xxxx.cloud.databricks.com
DATABRICKS_HTTP_PATH=/sql/1.0/warehouses/xxxxx
DATABRICKS_TOKEN=your_pat_here

OLLAMA_MODEL=llama3.2:3b
```

## 3) Build dbt manifest

This project loads governed metrics from `dbt/target/manifest.json`.

```bash
cd dbt
dbt deps
dbt build
dbt docs generate
cd ..
```

## 4) Run everything

```bash
docker compose up --build
```

- UI -> http://localhost:3000
- API -> http://localhost:8000
- Ollama -> http://localhost:11434

## Bring Your Own Data (Fork + Setup)

This repo is designed so you can fork it and point it at your own dataset.

You do not need to change backend logic to use your own data.
You only need to:
1. Update dbt models to match your tables
2. Define your semantic model + metrics in dbt
3. Update packs to reference your metric names and dimensions

### Minimum data requirements

Your warehouse should contain (or you should build via dbt) a fact table with:

Required columns for V1
- A timestamp column (e.g. `event_date`, `po_creation_date`)
- A numeric spend/value column (e.g. `amount`, `value_in_gbp`)
- A dimension for Top-N (e.g. `vendor_name`, `customer`, `product`)

Optional but recommended
- A category field to segment spend (e.g. `department`, `business_unit`, `lob`)

If you do not have "Digital Solutions", replace that concept with your own segment
(e.g. "Retail", "Cloud", "Marketing", "US Region").

### Step-by-step: adapt to your dataset

#### Step 1 - Point dbt to your warehouse

Update your `dbt/profiles.yml` to your environment.
For Databricks, the profile uses:
- `DATABRICKS_SERVER_HOSTNAME`
- `DATABRICKS_HTTP_PATH`
- `DATABRICKS_TOKEN`

Then verify:

```bash
cd dbt
dbt debug
```

#### Step 2 - Create or adapt your fact model

Create a dbt model similar to `fct_po_spend.sql` that outputs:
- `event_date` (date or timestamp)
- `amount` (numeric)
- `segment` (categorical, optional)
- `vendor_name` (categorical for ranking)

```sql
select
  event_date,
  vendor_name,
  segment,
  amount
from {{ ref('stg_your_source') }}
```

#### Step 3 - Define a semantic model

Create `dbt/models/marts/semantic.yml`:
- point model to your fact model
- define the time dimension
- define measures (e.g. `sum(amount)`)
- define dimensions (e.g. `vendor_name`, `segment`)

#### Step 4 - Define metrics

Define governed dbt metrics for V1:
- `total_spend` (simple)
- `segment_spend` (simple, filtered)
- `segment_share` (ratio)

Replace "segment" with your business meaning (department, region, product line, etc).

#### Step 5 - Generate the manifest

```bash
cd dbt
dbt docs generate
cd ..
```

#### Step 6 - Update Packs to match your metrics

Packs are in:
- `api/eng/packs/*.yml`

Update:
- `department_vs_company.yml` to point to your left/right metric names
- `top_n.yml` to point to your ranking metric + dimension

Example:

```yaml
intent: comparison
comparison:
  left_metric: retail_spend
  right_metric: rest_of_company_spend

intent: ranking
ranking:
  metric: total_spend
  dimension: vendor_name
```

```bash
docker compose up --build
```

## API contracts (V1)

### Ask endpoint

`POST /chat`

Request:

```json
{ "question": "Show total spend by month" }
```

Response types:
- `timeseries`: `series[]` + `chart`
- `ranking`: `ranking[]` + `chart`
- `unknown`: safe refusal

### Packs

`POST /packs/{packId}/run`

Packs return a consistent contract:
- `answer` (string)
- `chart` (type/unit/x/y)
- `series` OR `ranking`
- optional `kpis`
- optional `debug`

## One more thing (this will make BYO data actually easy)

To make the "no Digital Solutions" issue painless, the best V1 pattern is:

- Treat "Digital Solutions" as **just an example segment**
- In the README, call it `SEGMENT_A` vs `REST_OF_COMPANY`
- Tell users to rename metrics:
- `segment_a_spend`
- `rest_of_company_spend`
- `segment_a_share`

That way, the system stays generic, and the only work is dbt config + pack YAML updates.
